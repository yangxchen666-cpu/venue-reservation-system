## 2. 产品概述

### 2.1 产品背景

本项目定位为**学习 / Demo / 毕设项目**，目标是构建一个球场预定管理系统，覆盖「用户在线预定球场 → 场地管理员维护球场与核销 → 系统管理员全局管理」的完整业务闭环。

立项前已完成 GitHub 同类项目调研：

- SmartSportV / YuMQ / xiaoyouhui（273★/222★/193★）：微信小程序 + 微信云开发，国内主流路线但代码质量一般
- MeetHere（299★）：Spring Boot 2.2.2 + Thymeleaf，适合课设但技术栈旧
- BCMS（4★）：Next.js 15 + React 19 + FastAPI 类架构 + SignalR，技术栈最新最完整
- ep3-bs（215★）：PHP + Zend Framework 2，生产级老牌项目

综合调研结论，选定技术栈：**Next.js + Tailwind CSS（前端）/ FastAPI（后端）/ 本机 PostgreSQL（数据库）**，兼顾技术栈的现代性与学习价值。

### 2.2 产品定位

- 形态：Web 端管理系统（浏览器访问，本机部署运行）
- 业务：球场场地的信息展示、分时段预定、预定核销与全局管理
- 定位：轻量、功能闭环的学习型项目，不做商业化扩展（详见「4.2 非目标」）

### 2.3 产品目标与成功标准

| 目标 | 成功标准 |
|---|---|
| 业务闭环 | 注册 → 浏览 → 预定 → 核销的完整流程可走通 |
| 核心正确性 | 同一球场同一时段不可被重复预定（数据库层硬保证） |
| 权限隔离 | 三种角色权限边界清晰，场地管理员只能操作自己名下的球场与预定 |
| 学习价值 | 实践 Next.js 15 + FastAPI + PostgreSQL 现代技术栈 |

### 5.2 普通用户功能

| 编号 | 功能 | 需求描述 |
|---|---|---|
| F-USER-1 | 场地浏览 | 公开查看场地列表，无需登录 |
| F-USER-2 | 场地筛选 | 按类型、价格等条件筛选场地 |
| F-USER-3 | 场地详情 | 查看单个球场的详细信息（名称 / 类型 / 价格 / 开放时间 / 时段划分）（待确认） |
| F-USER-4 | 预定场地 | 选择日期后展示该日时段网格；时段网格由球场开放时间与时段长度生成（默认 60 分钟 / 时段，可配 30 分钟）；已订时段置灰不可选；确认后生成预定 |
| F-USER-5 | 我的预定 | 查看自己的预定列表 |
| F-USER-6 | 取消预定 | 取消自己的预定（取消时限待确认，见 Q-06） |

**时段网格交互规则（预约页 `/book/[courtId]`）：**

1. 日期选择器可选范围为「今天起 7 天」（待确认，见 Q-20）
2. 时段网格由 `open_time` / `close_time` / `slot_minutes` 计算生成（默认 60 分钟 / 格，可配 30 分钟）
3. 已订时段置灰且不可点击；当天已过时段置灰不可订
4. 点击可订时段 → 弹出确认信息（场地名 / 日期 / 时段 / 价格）→ 确认提交
5. 提交结果：成功（200）→ 跳转「我的预定」；冲突（409）→ 提示「该时段已被预约」并重新拉取该日期时段数据、刷新置灰状态
6. 未登录点击时段 → 引导跳转登录页，登录后回跳原场地页

## 7. 业务流程

### 7.1 预约流程

```
浏览 / 筛选场地 → 查看场地详情 → 选择日期 → 时段网格（已订时段置灰）
→ 选择可订时段 → 确认预定 → 生成预定 → 「我的预定」查看 → 取消（可选）
```

### 7.2 场地管理员申请流程

```
普通用户提交申请 → 生成申请记录（pending）→ 系统管理员审批
→ approved：申请人升级为 venue_admin
→ rejected：申请驳回
```

### 7.3 核销流程

```
场地管理员打开工作台 → 预定列表 / 日历视图定位预定 → 执行核销
→ 预定状态更新为已核销（状态设计待确认）
```

### 7.4 预定状态流转

```
已预定（创建成功）→ 已核销（管理员核销）
                  → 已取消（用户或管理员取消）
```

> 状态字段的具体取值待确认，见「12. 风险与待确认事项」。

## 8. 数据需求

### 8.1 实体定义

| 实体 | 关键字段 | 说明 |
|---|---|---|
| User | `id`、用户名、密码哈希、`role`（`user` / `venue_admin` / `admin`） | 系统账号，角色决定权限 |
| Application | `id`、`user_id`、`status`（`pending` / `approved` / `rejected`） | 场地管理员申请与审批 |
| Court | `id`、`owner_id`、名称、类型、价格、`open_time` / `close_time`、`slot_minutes` | 球场，`owner_id` 归属场地管理员 |
| Booking | `id`、`user_id`、`court_id`、`date`、`start_time`（+ 状态字段待确认） | 预定记录 |

字段级明细以实施计划 `models/` 注释为准，未明确的字段（状态、价格快照、图片等）见 12.2 待确认清单（Q-05、Q-11、Q-18）。

### 8.2 核心约束

**防超订（本系统核心数据约束）：**

- `bookings` 表对 `(court_id, date, start_time)` 建立唯一约束
- 创建预定的 INSERT 在事务内执行；唯一约束冲突（IntegrityError）返回 HTTP 409「该时段已被预约」
- 由数据库层硬保证，不依赖应用层判断

### 8.3 实体关系

- User 1—N Application（一个用户可多次申请）
- User 1—N Court（场地管理员拥有多个球场，`Court.owner_id`）
- User 1—N Booking（一个用户多条预定）
- Court 1—N Booking（一个球场多条预定，受唯一约束限制同时段仅一条）

## 9. 非功能需求

### 9.1 防超订（核心约束）

- 同一球场同一日期同一开始时段最多存在一条有效预定
- 并发预定同一时段时，必须保证仅一个请求成功、其余请求明确失败（HTTP 409），不允许出现重复预定
- 通过数据库唯一约束 + 事务实现，禁止仅依赖应用层查询判断

### 9.2 安全

- 密码使用 bcrypt 哈希存储，禁止明文
- 认证使用 JWT，接口按角色鉴权
- 数据权限：场地管理员的所有查询与操作按 `Court.owner_id == current_user.id` 过滤，只能访问自己名下的球场与预定；系统管理员不受限

### 9.3 性能（待确认）

- 常规页面与接口响应时间目标 < 1 秒（本机部署环境）（待确认）

### 9.4 兼容性

- 运行环境：Node.js ≥ 20 LTS、Python 3.12+、PostgreSQL 17 或 18
- 浏览器：现代浏览器最新两个大版本（待确认）

### 9.5 可用性（待确认）

- 时段网格直观区分可订 / 已订状态（已订置灰）
- 操作结果有明确反馈（成功 / 失败提示，如 409 冲突提示「该时段已被预约」）（待确认）
